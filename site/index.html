How Switchboard works, and where to start reading

Switchboard is an AI receptionist for several businesses at once. Each business gets its own receptionist agent with a name, a voice and a number. It answers the phone in a live voice, holds the conversation, answers from the business's own facts, takes messages, books callbacks and puts callers through. Underneath, a call router decides where calls go, keeps emergencies safe, and takes over whenever the agent can't.

The whole design rests on a few ideas. Hold on to them and the code will make sense:

1. Python talks and scores, .NET decides and acts

Python listens, thinks and speaks for the agent, and turns words into probabilities for the router. .NET owns the call, the tenant's data, every tool the agent asks for, and every routing decision, made in one pure C# function, DecisionEngine.Decide. That still works when Python is down.

2. Decide by cost, not confidence

Instead of "route if confidence > 80%", the engine asks "which choice has the lowest expected cost of being wrong?" Sending an emergency to voicemail costs 100. Sending billing to sales costs 1. The numbers live in configs/cost_matrix.yaml.

3. Every tenant is walled off

Five fictional businesses share one system. Their tenant id travels with every call, is signed before it crosses to Python, picks their own Redis stream, and is enforced by row-level security in Postgres.

4. Every failure has a planned outcome

A caller always ends up somewhere. If speech recognition fails the caller gets a keypad menu. If anything else throws, they go to the tenant's fallback department.

Where the time goes

The history is what the caller heard

An interrupted answer is cut where playback stopped. If the caller heard nothing, the agent's turn is dropped and the caller's two sentences become one, so the model never answers a question twice.

The router is the safety net

If the agent can't start, the router answers the call. If the model fails mid-call, the agent says so in its own voice and transfers. Pressing 0 always reaches a person.

One voice per business

Each tenant's YAML has an agent: block with a name, a Flux voice, a greeting, its facts, notes on each department and its own numbers. Publishing validates it. thornveld_vet.yaml

It can call out too

POST /v1/agent/calls has the agent phone someone with its own caller ID, starting from a purpose. Consent is required, and without a trunk it can only ring the softphone. OutboundCalls

    Chapter 5

    The decision engine

    DecisionEngine.Decide is about 70 lines and is the most important code in the repo. It takes probabilities over intents and returns one of four actions: Route, Reception, Clarify or Escalate. It has no I/O and no clock, so it's tested against shared golden vectors in both C# and Python.

    Try it: the engine on one tenant

    This calculator re-implements Decide and RouteCost for Thornveld Animal Hospital, one of the five fictional tenants, using the real cost matrix. Three intents are enough to see the behaviour: appointment goes to reception, billing to accounts, and emergency to the on-call vet. Move the sliders or pick a preset.

    → accounts
    → on-call vet

    Sliders are weights; the engine normalises them to probabilities. Costs above 10 run off the scale. Costs used: correct 0, unrelated department 2, non-emergency sent to the emergency line 8, emergency to the wrong live department 20, emergency to voicemail 100, reception 1, clarify 0.5, clarify on an emergency 5.

    Why it's built this way

    Rules sit above costs

    Property tests found that expected cost alone sends a caller with a 6% chance of an emergency to voicemail after hours: 100 × 0.06 is still less than 8 × 0.94. So a hard guard (emergency_voicemail_guard: 0.02) removes voicemail as an option. Tenants may raise the emergency costs, never lower them.

    Clarify is compared to routes, not to a threshold

    Asking a question costs 0.5, or 5 if it might be an emergency. The engine only asks when that's cheaper than its best guess. ADR 0002 explains the choice.

    Same logic in two languages

    decision.py:183 is a Python twin used for offline evaluation. Both must agree on tests/golden/decision_vectors.json, checked by DecisionVectorTests and the Python tests.

    One home for policy

    DecisionFlow.ResolveAsync wraps the engine: decide, escalate if asked, decide again. Voice calls and chat messages both call it, so they can't drift apart.

    The inference side

    The Python service exposes the three RPCs in inference.proto. It never decides anything. It reports what it heard and how likely each intent is, and it refuses any request whose tenant context signature doesn't match.

    Chapter 7

    The message path

    Chat messages use the same decision code as calls, with no audio. Comparing the two paths is a quick way to see which parts are about telephony and which are about routing.

    A message, in order

    1. Program.cs:99 checks the X-Hub-Signature-256 HMAC and returns 401 if it's wrong.
    2. The phone-number id resolves to a tenant, the message is queued, and the webhook answers 200 straight away.
    3. MessageProcessor drops duplicates using the message_dedup table, because providers deliver at least once.
    4. The thread's text goes to ClassifyText with a 2-second deadline.
    5. DecisionFlow.ResolveAsync decides, exactly as for a call.
    6. The reply goes to the outbox. In tests that's a mock you can read at /mock/outbox/{tenant}.

    Chapter 11

    Run it, then break it on purpose

    Reading goes faster once you've watched a call go through. Start the stack, run the end-to-end suite, then change one number in the cost matrix and see which tests complain.

    # one-time setup
cp .env.example .env
uv sync --python 3.12
uv run poe proto
uv run poe stack-up && uv run poe seed

# see it work: five tenants on real SIP calls, plus the webhook path
uv run poe e2e

# the fast loop while you read
dotnet test tests/dotnet/Switchboard.Tests.Unit
uv run pytest tests/python/test_decision.py

# see it fail safely
uv run poe failure

# talk to it: set HOST_LAN_IP, PHONE_SIP_PASSWORD and ASR_MODE=live in .env, restart,
# then sign a softphone in as "phone" and dial 101 to 105 for the agents, 111 to 115 for the router
uv run poe stack-up && uv run poe seed
uv run pytest tests/python/test_agent.py

    Three exercises that teach the code

    Lower the voicemail guard

    Set emergency_voicemail_guard to 0.2 and run the Python decision tests. The property test test_emergency_never_goes_to_voicemail should fail, which shows why the guard exists.

    Follow one decision in a trace

    Run poe e2e, then read a DecisionMade event through the API: GET /v1/conversations/{id}/events. Its stage_ms shows where the time went.

    Remove the tenant setting

    Run uv run poe mutation --only tenant. Each mutant deletes one isolation control and names the test that caught it.

    Talk over the agent

    Call 101 and start speaking halfway through Lerato's answer. Then read the conversation's events: the AgentSaid event is marked interrupted and holds only the words you heard.

    Add a sixth tenant

    Copy a YAML in configs/tenants/, give it a new number, seed, and call it with SIPp. You'll touch config, seeding, the dialplan and the e2e runner.

    Words you'll meet in the code

    DID
    The phone number that was dialled. It identifies the tenant.
    ARI · Stasis
    Asterisk's REST and WebSocket interface. A channel "in Stasis" is controlled by the gateway rather than the dialplan.
    chan_websocket
    Asterisk 22's channel driver that streams call audio over a WebSocket. The gateway reads and writes μ-law frames on it.
    DTMF
    Keypad tones. Used for the fallback menu when speech can't be trusted.
    Intent
    What the caller wants, from a fixed list of 17 (billing, emergency, appointment_book…). Each tenant maps intents to its departments.
    τ_llm · τ_clarify
    Cost thresholds. Below τ_llm the engine routes; above it, it asks the LLM; above τ_clarify it may ask the caller.
    Degraded
    Running without trustworthy speech. Thresholds are halved and questions offer the keypad.
    Fusion
    Combining the LLM's single answer with the scorer's probabilities, using how often the LLM's answer was right in the past.
    RLS
    PostgreSQL row-level security: the database itself hides other tenants' rows.
    Flux
    Deepgram's conversational models: speech-to-text that decides when a turn has ended, and streaming text-to-speech that outputs telephone audio directly.
    EagerEndOfTurn
    Flux's early guess that the caller has finished. The agent starts thinking on it, and only speaks once EndOfTurn confirms it.
    Mark
    A marker sent with the agent's audio. Asterisk reports it when playback reaches it, which shows how much the caller has heard.
    Barge-in
    The caller talks over a prompt; the gateway sends FLUSH_MEDIA to stop playback.
